Local consent-gated ledger (append-only JSONL in the platform data dir, CI-disabled, resettable). - apps/tolkin-web: Next.js 16 app. Redaction-first analyzer, 3-provider counts (o200k exact, Gemma exact, cl100k proxy labeled estimate plus or minus 10 percent), token visualizer (never fabricated for Claude), cost calculator, audit panel, MCP analyzer, LLMLingua-2 in-browser compression preview, /bench results page. No fetch except the opt-in BYOK verify; no browser storage.

Distribution and proof surfaces: a three-track reproducible benchmark (structural lossless, configuration MCP, lossy LLMLingua-2 at 0.7/0.5/0.33; caveman-shrink measured at 11.7 percent on the same fixtures; wilpel marked not-runnable-headless with reason; determinism contract enforced), six GitHub workflows (ci with a windows job, publish via OIDC trusted publishing, PR audit comments, weekly drift watchdog, bench dispatch, action dry-run), and a staged public companion repo under distribution/ (three agent skills: tolkin-audit, tolkin-slim, tolkin-optimize; Claude Code plugin manifests; a composite GitHub Action with sticky PR comments and fail-on gating; public README). The owner has not yet created the public repo.

The non-negotiable identity: honesty is the trust moat. Every number carries its tier label (identified = advisory estimate, realized = measured structure with estimated frequency, measured = ground truth from logs), every claim is input-token bounded ("output may vary"), Claude counts are labeled estimates, unpriced models are listed rather than guessed, and the benchmark publishes methodology before numbers. Privacy: zero network egress of user content; the ledger and ingestion are local-only, consented, resettable.

Real-machine proof point: stats ingested 169 real sessions, 97.3 percent cache hit rate, about 1.68B cache-read tokens, $1,357 priced cost, with claude-fable-5 and claude-opus-4-6 honestly surfaced as unpriced.

## 4. The review charter (answer all of these)

A. Cross-reference matrix. For EVERY distinct recommendation, command idea, metric, and warning in both researches, classify it: SHIPPED (tolkin does this today; cite the file), PARTIAL (a slice exists; state exactly what is missing), REJECTED (IMPROVEMENTS section 4 or PLAN records a deliberate decision against it; quote it and judge whether the research changes the calculus), MISSING AND WORTH IT (gap with real user value; argue why and sketch the smallest honest version), or MISSING AND NOT WORTH IT (gap that conflicts with the product's identity, privacy posture, or honesty rules; say so plainly). Examples you must cover, non-exhaustive: the Token Bill of Materials token classification (static, dynamic, duplicated, cacheable, uncacheable, loaded-by-default, quality-critical) versus tolkin's load profiles; cache doctor; mcp doctor versus tolkin mcp plus scan; skill lint with per-skill token budgets; ci install and budget gates (delta-versus-baseline PR comments, cacheability score) versus the existing tolkin-audit.yml and the distribution action; trace (LiteLLM, Langfuse, OpenTelemetry GenAI spans, provider usage APIs) versus tolkin's Claude Code plus Codex ingestion; route and model routing policy; compress guardrails versus the LLMLingua preview and lossy-track stance; output-policy modes (the Caveman-scoped terse mode); batch API guidance; cost_per_successful_task as the KPI versus tolkin's tier system; budgets and governance (per-agent, per-run, per-team caps); config generation from one source of truth (skills, rules, AGENTS.md from a canonical spec); hooks recommendations (PreToolUse guards, PostToolUse truncation); code-execution-with-MCP; sub-agent fan-out economics; progressive-disclosure skill auditing; the per-OS config surface lists (do the researches name config locations tolkin scan misses, like .windsurf/rules, promptfoo.yaml, litellm.yaml, .github/workflows as a token surface?).

B. Prompt caching deep dive (the owner's explicit priority). Today tolkin has: cache-aware pricing and cost math (5m and 1h write rates, read rates), the prompt-cache-miss-risk and sub-cache-threshold audit rules (volatile-prefix detection), MCP cold versus warm scenarios, and measured cache hit rate from real logs (the 97.3 percent number). The researches push further: prefix-layout analysis (static-first, dynamic-last ordering linting), provider-specific cacheability rules (exact-prefix semantics, Anthropic breakpoints up to 4, OpenAI automatic, Gemini implicit, Bedrock metrics), a cacheability score, TTL strategy advice (5m versus 1h write economics given observed session cadence, which tolkin's ledger plus ingestion could actually compute from real data, something none of the researches realized is possible), per-session cache-write waste detection from the logs tolkin already parses, and cache-layout advice for the configs tolkin already scans. Design question to answer concretely: what should a `tolkin cache` command (or audit-rule expansion, or both) do, what data does it need that tolkin already has versus needs new access to, what can be advised honestly versus what would require runtime interception that violates the analyze-and-recommend identity, and what is the smallest shippable slice with a measured story. Be specific enough that an execution agent could build from your section.

C. Gaps neither side saw. With both pictures held together, what does NEITHER the build NOR the researches cover that real users hitting spend caps need? Think: the researches' own caveats (denominator games, accuracy tradeoffs of aggressive optimization), tolkin's identity (could it VERIFY other tools' claims as a service, given it already measured caveman-shrink?), the agent-skills channel (tolkin's three skills teach measurement; should one teach cache hygiene?), and anything in your own knowledge of the space.

D. Usefulness and testing. The owner's question: what else should be done to test this so it is genuinely useful for people? Evaluate: is the benchmark persuasive to a skeptic; what would a beta with 5 strangers reveal that CI cannot; which onboarding moments would lose a non-technical user; does the action's PR comment earn its place in a busy repo; what is the minimal docs surface a public launch needs; and does anything in the product overpromise relative to what the researches verified (run the honesty audit both ways: the researches also document VENDOR-INFLATED numbers, so check tolkin never echoes one).

E. Verdict. One page: is the shipped product the right shape against the evidence? The researches converge on "measurement first, CI gates, cache layout, MCP and skill budgets; defer runtime proxies and autonomous rewriting." State plainly where tolkin agrees, where it leads (things the researches missed that tolkin already proves, like realized-savings accounting from real logs), and where it lags. Then propose the next phase: a prioritized I6/I7 candidate list, each item with its user, its honest metric, and a rough size.
