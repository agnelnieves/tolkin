## 2. The proposal you are evaluating

The owner's vision, stated faithfully. An additional, opt-in layer (a plugin, an extra install, a thing users choose) that uses a model running locally on the user's Mac to do what deterministic rules cannot: semantic analysis of the project directory, its packages and SDLC structure, the harness configs in scope (project-level and global), and the skill and instruction files tolkin already discovers, producing concrete artifacts: an optimization plan, draft skill files tuned to the specific project, config recommendations, plain-language instructions for what to change and why. A possible shape is a pre-flight check (`tolkin preflight`?) or a flag on existing commands that deepens analysis when a local model is available. It must serve technical users (flags, JSON, composability) and non-technical users (a wizard, plain-language artifacts, maybe an opening question about which kind of user you are; judge that idea on its merits). Hardware floor: the owner's company runs MacBooks, M2 minimum, so M2/M3/M4 must work and M5-only performance must not be assumed. Tolkin ships on Windows and Linux too; those platforms are explicitly LOW priority for this layer but the story must be stated, not ignored. Harness config divergence must be handled correctly; note that scan's catalog already distinguishes Claude Desktop (Claude/claude_desktop_config.json under the per-OS config dir, scan/mod.rs lines 134-142) from Claude Code (home .claude.json plus project .mcp.json and settings files), which was the owner's worry case; your job on this front is to verify the catalog's currency and find what it misses (OpenCode and JetBrains are absent today; .windsurf/rules and .clinerules arrive with A12). The owner suspects Google's Gemma is "too heavy"; treat that as a hypothesis to test, not a constraint (section 5 has evidence in both directions). The enabling moment is WWDC 2026: Apple's sessions on local agentic AI with MLX canonized the exact stack this layer would ride.

The thesis to test, stated so you can attack it: tolkin's deterministic core measures structure; a local model adds semantic judgment (is this skill trigger vague, are these two instruction files paraphrases of each other, which spans of this prompt are static versus volatile, what does this project's stack imply about which skills it needs) at zero marginal token cost, zero API fees, zero egress. The Claude research in Tokens.md already sanctions a pattern like this (capability 2, around line 453: hand the deterministic scan summary to the user's already-installed agent for the optional optimization step). That pattern has two flaws tolkin can fix: the user's cloud agent burns paid tokens to do the optimizing, and it ships content to a vendor. A local sidecar does neither. Nobody ships this today (section 5, competitive scan). The question is whether small local models are actually competent enough, fast enough on M2-class prefill, and containable enough to be worth an opt-in layer, or whether this is a demo that disappoints on a base M2 Air.

## 3. The constraints that bind any design (thread these, never relitigate them)

1. "Do not put LLM calls in the analyzer" (REVIEW-FINDINGS.md, quality-evals matrix row, MISSING-NOT-WORTH-IT). The deterministic surfaces must remain bit-identical when the layer is absent, declined, or broken. That rejection was written about API calls and quality evals; the LLMLingua-2 preview proves opt-in local ML with explicit disclosure is acceptable. Your design must define the separation contract precisely: what the model may read, what it may emit, and the guarantee that no deterministic output, exit code, or CI gate ever depends on it.
2. Analyze and recommend, never intercept; no autonomous rewrites (Layer-3 automatic rewrites REJECTED in REVIEW-FINDINGS; skills apply edits only with user confirmation). Model-drafted artifacts are proposals presented as diffs, never silent edits.
3. Zero network egress. Loopback-only model traffic preserves the promise; the design should enforce it (refuse non-loopback base URLs without an explicit override). Model weights flowing INTO the machine are a download, not egress, but they require the LLMLingua-style explicit consent with size disclosed, and here the sizes are 0.6 to 20GB, not 58MB.
4. The ingestion privacy posture stores counts and timestamps, never content (usage/types.rs; the cost_per_successful_task rejection cites content being off-limits). A local model reading transcript or file CONTENT is a new consent class even though nothing leaves the machine. IMPROVEMENTS.md section 4.3 rejects SILENT privacy changes; explicit, documented, resettable consent is the bar it sets. Adjudicate: design the consent class that satisfies it, or conclude content stays out of scope and say what that costs the layer.
5. Tier vocabulary is exact. Model output is none of identified, realized, or measured. Design its label (a distinct advisory class that is never summed with the tiers) and its presentation so a model suggestion can never masquerade as a measurement.
6. Never relitigate IMPROVEMENTS.md section 4 or the rejections register in REVIEW-FINDINGS (runtime proxies, autonomous rewriting, cost-per-task KPI, repo packing as a product, fabricated Claude visualization). If your best design conflicts with one, surface the conflict explicitly instead of averaging around it.
7. The repo content rules bind your report: no em-dashes or en-dashes anywhere, no AI attribution, plain factual voice, never link the private repo by URL.
8. Toolchain posture for any implementation sketch: the npm base install must not grow (the layer talks HTTP to a sidecar; ureq is already in-tree), no Python in the base install ever, no node-gyp, Rust-first. A separate opt-in install step for the sidecar is fine and expected.

## 5. The MLX landscape, grounded (a prior research pass; verify what you rely on)

Stack. mlx-lm (Python, v0.31.3 as of 2026-04-22) ships `mlx_lm.server`, an OpenAI-compatible HTTP server on 127.0.0.1:8080 with /v1/chat/completions and /v1/models, continuous batching upstream (--prompt-concurrency 8, --decode-concurrency 32 defaults), per-family tool-call parsing, speculative decoding, a prompt cache holding up to 10 KV caches, and --max-tokens defaulting to 512 (must be raised for artifact generation). Critical gap: upstream has NO response_format/json_schema constrained decoding as of 0.31.3 (verified by reading server.py; recheck against main). Schema-reliable JSON therefore needs prompt discipline plus local validation and repair in Rust, or a different backend: llama.cpp's llama-server has the strongest portable json_schema/GBNF story, LM Studio and Ollama both document structured output. SERVER.md warns the server is not production-hardened; treat it as a loopback-only child process whose output is untrusted input. Models auto-download from HuggingFace into ~/.cache/huggingface/hub. Sources: github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md, ollama.com/blog/mlx, lmstudio.ai/docs/developer/openai-compat/structured-output, github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md.

Hardware reality, the part that gates everything. Prefill (prompt processing) is compute-bound and is exactly what repo-scale analysis stresses: tens of thousands of tokens in, short artifacts out. The WWDC headline (prompt processing roughly 4x faster) is M5-only silicon (GPU neural accelerators; Apple measured TTFT 3.3-4.1x vs M4, decode only ~1.2x). M2 through M4 get none of that, only the software wins (batching, prompt/KV caching, speculative decoding). Measured anchors: llama.cpp's canonical table (7B Q4, github.com/ggml-org/llama.cpp/discussions/4167) puts prefill at ~180 tok/s on base M2, ~221 on base M4, ~440 on M4 Pro, ~886 on M4 Max; MLX runs ~1.2-1.5x faster than that; throughput degrades ~20 percent by 32k context (github.com/ml-explore/mlx/discussions/3209). Derived estimates (label them as such): a 32k-token prompt into a 4B model takes roughly 80-130 seconds on a base M2, 35-55 seconds on M4 Pro, 17-27 seconds on M4 Max; a 14B model is 4-6x worse. MoE models with ~3B active parameters (Qwen3-Coder-30B-A3B, Qwen3.5-35B-A3B, gpt-oss-20B) prefill like small models while answering like large ones, the best trade available, but need 18-22GB and therefore 32GB machines. Memory: macOS caps GPU wired memory near 66-70 percent of unified RAM below 64GB, so an 8GB machine has a ~5.3GB ceiling shared with everything else; 8GB is degraded mode at best (0.8-2B models, short chunks), 16GB is the honest floor (a 4B 4-bit model plus quantized KV alongside an IDE), 32GB opens the MoE tier. Ollama gates its new MLX backend to 32GB+ machines, a telling vendor signal. Design consequences: chunked map-reduce analysis in 4-16k segments instead of monolithic prompts, exploit the server prompt cache for the static prefix, print an upfront time estimate from chip plus model plus token count, and never size UX promises to WWDC demo hardware.

Model candidates (params, 4-bit RAM, license, fit). Qwen3.5 dense family 0.8B/2B/4B/9B (0.6/1.6/2.3/5.6GB), Apache 2.0, the WWDC demo family, strongest small-model JSON and tool-calling reputation: the default candidates per tier. Qwen3-Coder-30B-A3B and Qwen3.5-35B-A3B MoE (18-22GB), Apache 2.0, the 32GB-tier workhorses. gpt-oss-20B (12-13GB MXFP4), Apache 2.0. Phi-4-mini 3.8B, MIT. Gemma: the owner's instinct is half right; Gemma 3 12B/27B are indeed too heavy for 16GB and Gemma 3's custom license carries commercial-use flow-downs that a shipping product should not casually absorb (ai.google.dev/gemma/terms), but Gemma 4 moved to Apache 2.0 and its E2B/E4B edge models are among the cheapest credible options for 8GB machines. Avoid reasoning-distill models (R1-style) for artifact generation: think-token bloat multiplies latency and breaks strict JSON without extra parsing. Llama carries the community-license attribution and naming obligations; not worth it given Qwen exists. Verify current releases on huggingface.co/mlx-community before blessing anything; several 2026 model claims trace to SEO-grade secondary sources.

Backend-agnostic shape (this likely resolves the Windows/Linux question nearly for free). Every serious local backend speaks OpenAI-compatible HTTP on loopback: mlx_lm.server :8080, Ollama :11434 (MIT, runs MLX on Apple silicon 32GB+ and llama.cpp elsewhere, best download UX), LM Studio :1234 (free for work use since July 2025, RAM-fit badges, headless daemon), llama-server (everywhere, strongest structured output). A {base_url, model} config surface with auto-detection probes against /v1/models, MLX blessed as the documented fast path on Apple silicon, and Ollama or llama-server documented for other platforms, keeps tolkin backend-neutral and the egress promise intact. Integration precedents to copy: Xcode 26's Settings, Intelligence, Locally Hosted provider (it does NOT manage model downloads, the minimal-responsibility precedent), Zed's auto-discovery of pulled models, Continue.dev's per-model roles (small model for classification, larger for generation), LM Studio's fits-your-machine badges, and WWDC session 232's OpenCode-over-localhost demo. Competitive scan: no shipping product uses a local LLM to optimize tokens, prompts, or harness configs as of June 2026; the neighbors are deterministic packers (Repomix, explicitly no-LLM), the LLMLingua research line (library, not product), cloud-side context features (Factory.ai, /compact), and hand-written advice packs. White space, with the obvious fast-follow risks.

## 6. The research charter (answer all of it)

B. Task architecture: what the model actually does. Inventory candidate tasks and score each on four axes: small-model competence (cite evals, or design the quick local eval that would settle it), marginal value over the deterministic engine (the tree-sitter counterexample applies: if structure can do it, the model should not), verifiability (the governing pattern is model proposes, Rust verifies: re-tokenize, re-measure, diff, schema-validate; a suggestion that cannot be deterministically checked is a liability), and failure containment. Candidates, non-exhaustive: static-versus-volatile span classification feeding the I7-1 cacheability score (the sharpest roadmap intersection: regexes catch timestamps and UUIDs, a model judges whether a paragraph is session-specific); skill-file lint beyond the static budget rule (trigger specificity, body verbosity, example bloat, the Tokens.md skill-lint spec); cross-file paraphrase dedup across global and project instruction files (the Model2Vec slot: evaluate embeddings via MLXEmbedders or similar versus a generative judge; embeddings are cheaper, more deterministic, and may win outright); CLAUDE.md/AGENTS.md instruction audit (contradictions, stale paths cross-checked deterministically against the repo, instructions that restate defaults); SDLC-aware draft skill generation from the project's actual stack (deterministic manifest parsing decides WHAT is relevant; the model only drafts, output schema-validated the way check-skill-schemas.ts already validates skills, presented as diffs); plain-language narration of existing deterministic findings for non-technical users (lowest risk, possibly highest immediate value); map-reduce repo summarization for the project command's docs profile. For each surviving task: the chunking strategy under the prefill budget, the JSON contract plus local validation and repair (remember upstream mlx-lm lacks json_schema), the artifact it emits, and the deterministic check that gates presenting it.

C. Integration architecture. Recommend the v1 shape and defend it: sidecar detection first (probe :8080/:11434/:1234 for /v1/models), spawn a supervised mlx_lm.server child only if installed and consented, never bundle weights, download consent with size, disk path, and RAM-fit shown (the LM Studio badge as a CLI table), loopback enforcement, offline and server-death behavior, uninstall story (what to delete, including HF cache paths). Packaging: opt-in plugin semantics, zero new base-install weight, config in the existing config.toml, consent recorded like the existing consents. Concurrency: continuous batching means parallel chunk analysis is real; size the default.

D. Experience design for both audiences. The pre-flight that asks whether the user is technical: evaluate it against alternatives (infer from invocation context; progressive disclosure; one wizard with sensible defaults and an expert flag). Define the non-technical golden path end to end (they should end with a plain-language optimization plan and confirmed, diffed config changes, then a re-measure that shows the delta in the ledger) and the technical path (--json everywhere, individual task flags, composable with the existing commands). State the Windows/Linux story in one paragraph: presumably the same layer pointed at Ollama or llama-server, unblessed and undocumented-as-fast, or explicitly deferred; pick and justify.
