# Tolkin Cross-Reference Review: Findings

Review date: 2026-06-10. Reviewed: tolkin 0.9.0 (repo state at commit bb7395e) against the two independent researches in /Users/agnel/Downloads/Tokens.md (the "ChatGPT" tokopt blueprint and the "Claude" competitive landscape), both written with zero repo knowledge by design. Every claim below cites a file, a command output, or a research line. Findings carry P0 (wrong or misleading today), P1 (high-value gap), P2 (worth considering).

## Executive summary

1. P0: the repo's own PR-audit workflow is parse-dead. `.github/workflows/tolkin-audit.yml` has two top-level `env:` keys (lines 14 and 25, introduced by the rename commit 168fe98); GitHub rejects the file and every push since shows a 0-second failure ("This run likely failed because of a workflow file issue", run 27307192065). The next PR gets no audit comment.
2. P0: tolkin contradicts itself on cache discounts. `tolkin mcp --provider openai` models warm cache at 50 percent of cold (mcp.rs:757) while `tolkin cost --model gpt-5.4 --cache-hit-rate 1` bills cached input at 10 percent of base (pricing.rs:111). Both were live-proven with the same binary. Gemini disagrees the same way (0.25 warm vs no modeled discount).
3. P1: the three staged public skills drifted from the shipped JSON contracts: tolkin-audit names two rule ids that no code emits, tolkin-optimize documents a `stats --json` schema whose keys do not exist, and all three carry stale 0.7.0 versions.
4. P1: the staged distribution/README understates the product (win32 marked pending while tolkin-win32-x64@0.9.0 is live) and points at a benchmarks file the public repo will not contain.
5. P1: the benchmark's configuration track is labeled "measured" but its cold-token numbers are catalog estimates, while methodology.md promises counts "against a catalog of real, public server manifests". A skeptic will find this first.
6. P1: the cost calculator's default total is 97 percent estimated output volume (the output:input price ratio reused as a token-volume ratio), which sits awkwardly against the input-token-bounded identity.
7. Against the researches' convergent blueprint (measurement first, CI gates, cache layout, MCP and skill budgets, defer runtime proxies and autonomous rewriting), tolkin agrees on identity and leads on honesty machinery: the three-tier vocabulary, the token-for-token log reconciliation, and the reproducible benchmark have no equivalent in either research.
8. Tolkin's biggest lag is exactly the owner's stated priority: prompt-cache analysis. The section below specifies a `tolkin cache` command whose core insight neither research saw: tolkin's consented logs already contain everything needed to compute TTL economics and cache-write churn from ground truth.
9. Second-biggest lag: the CI gate compares nothing. The action reports absolute state; the researches' delta-versus-baseline PR comment with token budgets is the strongest idea tolkin has not shipped.
10. Recommended next phase: fix the P0s and P1s (small), ship cache slice 1 (measured cache health plus TTL counterfactual), add delta gates to the action, then tools/list ingestion for exact MCP counts.

## Verdict

**Is the shipped product the right shape against the evidence? Yes, with two corrections and one priority.**

Both researches, written blind to this repo, converge on the same architecture tolkin already has. The tokopt blueprint's "highest-ROI MVP" list (Tokens.md lines 341-351) names seven items: a repo/workstation scanner, a token bill of materials, an MCP linter, a PR-comment GitHub Action, a cache layout checker, a usage importer, and scoped output-policy modes. Tolkin ships the scanner (`tolkin scan`, 16 client locations, scan/mod.rs:137-284), most of the bill of materials (`tolkin project` load profiles, project.rs), the MCP linter with verified slim mechanisms beyond what the research asked for (mcp.rs catalog with snippets), the Action (distribution/action/action.yml, currently parse-dead in this repo, see P0-1), a slice of the cache checker (two audit rules), and a two-source usage importer with dedup semantics more correct than the incumbent's (IMPROVEMENTS.md section 4.6). The seventh item, output-policy modes, tolkin deliberately rejected (IMPROVEMENTS.md section 4.1), and the Claude research independently validates that rejection by measuring output compression at 1-3 percent of a real bill (Tokens.md line 392).

The Claude research's strategic blueprint (line 448) describes tolkin almost verbatim: "a script-based auditor plus config generator plus measurement harness, not a runtime proxy first", "script-first (deterministic scans, no LLM calls for analysis)". Tolkin's Rust core makes zero LLM calls, and its only sanctioned egress is the opt-in BYOK verify (apps/tolkin-web/CLAUDE.md). The convergence is strong evidence the shape is right.

**Where tolkin leads (things neither research has):**

- The three-tier vocabulary (identified, realized, measured) with a published, reproducible formula (tiers.rs module rustdoc). Both researches say "measure before and after" (Tokens.md lines 467, 481); neither defines what kind of number a "saving" is. Tolkin's tier system is the only artifact in this entire problem space that does.
- Measured ground truth reconciled token-for-token against an independent recompute (PROGRESS.md, I2 entry: 169 sessions, cache_read 1,676,359,510, exact match on every field), with the last-wins dedup fixing a known incumbent bug.
- A determinism-contract benchmark that vendors external comparators verbatim and labels what it cannot run (RESULTS.md lines 79-82) instead of estimating it. The Claude research built its vendor-claim-versus-verified table by hand once; tolkin's harness is that table, reproducible.
- The realized-savings loop closed through agent skills (apply, re-measure, report with tier labels), which neither research proposes.

**Where tolkin lags:**

- Prompt caching depth. Two audit rules and cache-aware pricing exist, but no layout analysis, no cacheability score, no log-based cache health, no TTL guidance. Both researches rank caching as the largest single lever (lines 10-12, 385). The deep dive below is the answer.
- CI gating. The action reports state; the researches gate deltas against a baseline with budgets (lines 166-190, 283-300). This is the highest-leverage small feature tolkin lacks.
- Per-tool MCP inspection. The analyzer prices servers from a curated catalog; the researches inspect tool descriptions (line 17: 97.1 percent of 856 tools had description smells). Without tools/list ingestion, tolkin cannot see inside a server. PLAN section 11 promised `--live-probe`; the shipped CLI has no such flag (verified via `tolkin mcp --help`).
- Model-mix awareness. Routing as a runtime concern is rightly out of scope, but tolkin already has by-model measured data and surfaces no advisory on it (the Claude research's thresholds at line 474 are directly computable from `stats`).

**The decisive judgment:** the researches would have tolkin build the same product, minus the honesty machinery they did not think of, plus the cache and CI-delta layers it has not built yet. The identity (analyze and recommend, never intercept; every number labeled; zero egress) survives contact with both documents intact. Build the cache layer next; it is the one place where the product's strongest asset (consented real logs) and the researches' strongest recommendation (cache layout first) intersect, and nobody else can do it locally.

## Findings register (P0 and P1 detail)

### P0-1: tolkin-audit.yml is parse-dead on GitHub

- Evidence: two top-level `env:` blocks at .github/workflows/tolkin-audit.yml:14 (`FORCE_JAVASCRIPT_ACTIONS_TO_NODE24`) and :25 (`TOLKIN_FAIL_ON`). Duplicate mapping keys make the workflow file invalid to GitHub's parser.
- Independent confirmation: `gh run list --workflow=tolkin-audit.yml` shows every run since the rename merge completing in 0s with conclusion failure, on push events the workflow does not even subscribe to (the signature of a file-level parse error); `gh run view 27307192065` reports "This run likely failed because of a workflow file issue."
- Introduced by: commit 168fe98 (the rename, which also carried the Node-24 migration; `git log -S FORCE_JAVASCRIPT_ACTIONS_TO_NODE24`). The other five tolkin workflows have exactly one `env:` each (grep verified) and are unaffected.
- Impact: the PR-audit proof surface the product story leans on (IMPROVEMENTS.md section 0 lists "tokler-audit (PR comments on this repo)" as built) silently stopped existing, and every push to main shows a red run.
- Fix: merge the two blocks into one `env:` mapping carrying both keys. One-line-class change; re-verify with a draft PR.

### P0-2: cache discounts disagree across tolkin's own surfaces

- Evidence A: pricing.rs models OpenAI cached input at 10 percent of base for the whole GPT-5 family (gpt-5.4: input 2.5, cache_read 0.25, pricing.rs:109-111) and models no Gemini cache discount at all (cache_read: None, pricing.rs:149).
- Evidence B: mcp.rs `scenarios()` hardcodes warm multipliers of 0.50 for OpenAI and 0.25 for Gemini (mcp.rs:752-758).
- Live proof, same binary: `tolkin mcp fixtures/configuration/mcp-heavy.json --provider openai --json` reports warm/cold = 0.5 while `tolkin cost - --model gpt-5.4 --cache-hit-rate 1` bills cached input at exactly 10 percent of base ($0.25 per MTok against $2.50). Both numbers ship to users today (the web MCP panel uses the same core via WASM).
- Adjudication of the underlying research contradiction: the Claude research states "OpenAI: ~50% automatic discount" (Tokens.md line 424) while the ChatGPT research's worked example prices GPT-5.5 cached input at 10 percent of base ($5.00 versus $0.50, line 21). These are both right for different model generations; the 50 percent figure belongs to the pre-GPT-5 era. For the models tolkin actually catalogs, the pricing table's 10 percent is the defensible number and mcp.rs's 0.50 is stale. For Gemini, both researches document context caching as available with discounts (lines 91, 424), so mcp.rs's 0.25 is closer to current reality than pricing.rs's None; the cost calculator's note "No published cache-read discount for this model" (cost.rs:145) likely overclaims and should be re-verified at the next pricing refresh.
- Fix: derive the warm multiplier in `scenarios()` from `pricing::default_for(provider)` (cache_read over input) instead of hardcoding, and settle the Gemini cache stance once, in pricing.rs, with the refresh date bumped. Anthropic is already consistent (0.10 both places) and unaffected.

### P1-1: the staged public skills document contracts the product does not have

- tolkin-audit SKILL.md step 3 names rules `oversized-skill-body` and `shell-export-secret` as "common rules" under `findings_by_rule` (distribution/skills/tolkin-audit/SKILL.md:94-95). Neither string exists anywhere in product code (grep over apps/tolkin-cli/src and packages/tolkin-core returned zero hits). The 13 real rule ids are enumerated at audit.rs:347-1120. Secrets actually surface under `secret_files`, not as audit rules (verified in live `tolkin project . --json` output).
- tolkin-optimize SKILL.md step 1 documents a `stats --json` shape with keys `project.snapshots`, `realized.delta_tokens`, `realized.sessions_estimated`, `realized.total_tokens_saved`, `realized.tier` (distribution/skills/tolkin-optimize/SKILL.md:44-61). The real output has none of these: top-level keys are scope, project_key, generated_at, prices_observed, realized_rate, ledger, ingestion, tiers; realized fields are tokens, usd, sessions_basis, sessions_count, since (live run verified; stats.rs:85-102, tiers.rs:152-169).
- tolkin-audit SKILL.md also says near-duplicate detection finds "repeated blocks across files" (line 93); the project command runs the audit per file (PROGRESS.md, project entry: "Per file: exact o200k count, audit findings"), so cross-file duplication is not detected.
- All three skills carry `metadata.version: 0.7.0` against a 0.9.0 product and a README that pins the action at 0.9.0.
- Impact: the skills are the agent-facing API. PROGRESS.md's I5 entry claims they teach agents to "parse the real emitted fields"; for tolkin-optimize that claim is false today. An agent following these instructions will mis-parse or fabricate.
- Fix: regenerate the three schema blocks from live `--json` runs, and add a distribution lint (CI or pre-publish script) that extracts each documented JSON key and asserts it appears in real command output. That turns this class of drift into a gate.

### P1-2: distribution/README launch blockers

- The support matrix says Windows x64 "Binary built; npm platform package pending first publish" (distribution/README.md:136) while PROGRESS.md's npm-cutover entry records tolkin-win32-x64@0.9.0 live on the registry. The staged public repo understates the product on day one.
- The quickstart's first example is captioned "Count tokens in a file" above `npx tolkin-cli scan` (README.md:16-17); scan discovers local configs and takes no file.
- The README closes with "see `benchmarks/RESULTS.md` in this repository" (README.md:125-126), but distribution/ stages no benchmarks directory (file inventory verified); IMPROVEMENTS W6a promised a "benchmark results mirror" in the companion repo. Either stage the mirror or point at the /bench URL.
- Fix: three small edits plus the mirror decision, before the public repo is created.

### P1-3: the configuration benchmark track overstates its evidence class

- methodology.md (track 2) says the track "counts that weight against a catalog of real, public server manifests". What ships counts nothing: the cold numbers come from `tolkin mcp`, whose per-server costs are curated representative estimates (mcp.rs:123-126 "Representative cold-cache token cost"; the analyzer's own output note says "Cold-cache token costs are representative catalog estimates", mcp.rs:707). RESULTS.md discloses "the analyzer's catalog is the source of truth" (line 69) but still fills a "Tokenizer" column with "o200k_base via tolkin mcp", and the /bench page metadata calls all three tracks "Measured, reproducible" (bench/page.tsx:20).
- Why this is P1: the benchmark is the rigor story (IMPROVEMENTS section 2: "The viral tools have claims; Tokler will have a methodology"). The structural and lossy tracks genuinely measure; the configuration track is the one a hostile reader will catch, and it is the headline wedge.
- Fix options, either honest: (a) vendor real tools/list manifests as fixtures and tokenize them (pairs with the tools/list ingestion feature below), upgrading the track to actual measurement; or (b) reword methodology.md track 2 and the page description to "catalog-estimate based, refreshable" and drop the tokenizer attribution from those rows. Option (a) is worth the work; it also fixes the catalog's staleness story.

### P1-4: the cost calculator's default total is dominated by a fabricated output estimate

- cost.rs:129-132 estimates output tokens as input_tokens times the output:input PRICE ratio (model.output / model.input). PLAN section 10 defines that 5x/6x/8x figure as a price ratio; the implementation reuses it as a volume ratio.
- Live proof: 1,001 input tokens on gpt-5.4 yields estimated output of 6,006 tokens, and the estimated output is 97 percent of the displayed per-call total. Paste a 100K-token document and the default view implies a 600K-token response.
- The estimate is disclosed (output_estimated flag, "~" prefix on the web, an honesty note), so this is not silent, but the default behavior of the input-token analyzer is to show a number that is 97 percent output guess, and PLAN's own worked example (section 10: Sonnet, 20K prompt, $6.00/hr) is input-only.
- Fix: default to input-side cost with output as an explicit opt-in (set output tokens or pick an output preset), or calibrate the default volume ratio from tolkin's own measured logs and label the basis. Either change makes the headline number match the product's input-bounded identity.

### P1-5: the Tool Search scenario and the GitHub catalog note disagree in the same report

- mcp.rs computes tool_search as a flat 500 + min(tools, 5) x 600 = 3,500 for every server with five or more tools (mcp.rs:761-763), while the GitHub entry's user-visible note says "behind Tool Search this drops to about 8.7K" (mcp.rs:150, sourced from PLAN section 9). Both render in one `tolkin mcp` output (live verified: github scenario tool_search 3,500, note says 8.7K).
- Fix: scale the stub estimate (for example, stub plus a per-tool deferred-load share derived from the server's cold cost) or align the note; today the report disagrees with itself by 2.5x on its flagship example.

## Prompt caching deep dive (the owner's priority; execution-ready)

### What exists today

- Pricing: per-model cache_read, cache_write_5m, cache_write_1h for all four Anthropic models, cache_read for the GPT-5 family (pricing.rs:42-140). Multipliers verified internally consistent for Anthropic (0.1x read, 1.25x and 2x writes).
- Cost math: cache_hit_rate, cache_write_tokens, cache_ttl inputs (cost.rs:38-52).
- Audit rules: volatile-prefix (timestamps, epoch seconds, UUIDs, session-id hex in the first 1KB; savings_max 90 percent of input; audit.rs:601-667) and sub-cache-threshold (256..1024 tokens with a reuse heuristic; audit.rs:673-706).
- MCP scenarios: cold/warm/Tool-Search per server (mcp.rs:752-770), subject to P0-2.
- Measured ground truth: cache_hit_rate = cache_read over input-side (tiers.rs:172-183), the 5m/1h write split preserved end to end (types.rs:31-37), real-machine proof of 97.34 percent across 169 sessions with all 43.87M write tokens at the 1h TTL and zero at 5m (PROGRESS.md I2 reconciliation table).

### What the researches add that tolkin lacks

Prefix-layout ordering rules (static first, dynamic last; Tokens.md lines 74-91), provider-specific cacheability semantics (exact-prefix matching, Anthropic's up-to-4 breakpoints and tools-then-system-then-messages order, OpenAI automatic 1024+ prefix caching, Gemini implicit caching, Bedrock's cacheReadInputTokens/cacheWriteInputTokens metric names; lines 91, 424), a cacheability score on PR comments (line 180), TTL economics (line 11: "whether long TTLs are worth it"), an actionable hit-rate threshold ("cache hit rate under 0.5 over a normal hour means it's broken", line 473), and cache-invalidation pitfalls (one timestamp before the breakpoint invalidates the prefix; serialize tool order deterministically; line 483).

And the thing neither research realized: they both treat TTL choice and cache health as things to reason about from documentation. Tolkin's consented ingestion already parses per-request records carrying timestamp, cache_read, and the 5m/1h cache_creation split (claude_code.rs:305-348). Nobody else in this space has local ground truth to compute these answers from.

### Design: `tolkin cache` plus rule upgrades

**Surface 1: `tolkin cache [--global] [--json]` (measured mode; requires ingestion consent).** A cache-health report per project and machine-wide:

1. Hit rate with the cited threshold: report the measured rate and, when it is below 0.5 over any active day, the "caching is likely broken" advisory with the research-grade citation. Tier: measured. Data: already aggregated.
2. Write churn (prefix instability caught in the act): within a session, every cache_creation event after the first means the prefix changed. Report writes-after-first as a share of write tokens per session, and name the worst sessions. A volatile prefix stops being a heuristic and becomes an observed event. Tier: measured. Data: needs per-request retention (below).
3. TTL economics, computed not guessed. For a stable prefix, a 5m-TTL strategy re-writes after every gap above 5 minutes; a 1h strategy re-writes only after gaps above an hour, paying a 2x write instead of 1.25x. With W5 = writes under the 5m strategy and W1 = writes under the 1h strategy (both directly countable from the observed gap sequence, since reads refresh the TTL), the comparison reduces to: the 1h TTL is cheaper exactly when 1.9 x W1 < 1.15 x W5, that is when W1/W5 < about 0.6. In words: 1h pays when more than roughly 40 percent of your cache-expiring gaps land between 5 minutes and an hour. Tolkin should compute the observed gap distribution per project, evaluate both strategies on the real timeline, and report the dollar delta at the pinned rates. Labeling: the gap distribution and observed write volumes are Tier 3 (ground truth); the counterfactual delta is a Tier 1 advisory estimate computed from Tier 3 inputs, and the report must say exactly that.
4. Cadence facts that make the advice concrete: share of intra-session gaps over 5 minutes, share of inter-session gaps under an hour (whether a 1h cache ever survives between sessions), and sessions with zero cache reads (caching not working at all, the misconfigured-pipeline case).
5. Honest scope line, always printed: Claude Code manages its own caching, so for Claude Code sessions the actionable levers are prefix stability and session shape; TTL choice is a direct lever only for API pipeline builders (tolkin's primary audience per PLAN section 1).

**Surface 2: rule upgrades (static mode, no logs needed).**

6. volatile-prefix v2: today the rule checks only the first 1KB and flags presence (audit.rs:634-648). Upgrade: find the FIRST volatile match anywhere, and report the tokens downstream of it as the invalidated span, because everything after the first changed byte falls out of the prefix. The savings bound becomes specific instead of "up to 90 percent".
7. Cacheability score (0 to 1) per file and per assembled prefix: start from 1.0 and subtract weighted penalties for (a) the share of content downstream of the first volatile token, (b) a sub-1024-token stable prefix, and (c) unstable MCP server args (env-interpolated or timestamped args detectable in scanned configs). Emit it in `project --json` and the action's PR comment so the CI delta gate (below) can watch it. This is the tokopt PR-comment field (line 180) made real.
8. Provider semantics in the notes, cited: Anthropic exact-prefix with up to 4 breakpoints and tools-system-messages order; OpenAI automatic with the 1024 minimum; Gemini implicit; Bedrock metric names for users normalizing their own telemetry. Static text plus citations; no measurement claims.

**What tolkin already has versus needs:**

- Already has: the log files (consented, read-only), the 5m/1h split per record, per-record timestamps and cwd, the pricing table, the scanned configs, the audit engine. No new data access of any kind is required for surfaces 1 and 2.
- Needs (a code change, not an access change): per-request retention in the reader. Today SessionUsage keeps only aggregates (types.rs:62-80). Add a compact per-session vector of (ts, fresh, cache_read, write_5m, write_1h) tuples, or precomputed gap/churn summaries if size matters; bump the parse-cache version to v3 (the v1-to-v2 self-healing pattern already exists, PROGRESS.md I2 entry). Privacy class unchanged: token counts and timestamps only, the exact posture types.rs:3-5 already states.
- Out of bounds, stated plainly: predicting a post-fix hit rate (depends on runtime behavior tolkin does not control), inserting or moving cache_control breakpoints in live requests (runtime interception; the identity is analyze and recommend), and any per-request advice for Claude Code's internal prompt assembly (closed runtime). These belong to gateways, and both researches agree proxies come last (lines 353, 379).

**Smallest shippable slice with a measured story:** surface 1 items 1, 2, and 4 plus the TTL counterfactual (item 3), validated the I2 way: an independent recompute over this machine's real logs must match field for field. The launch story writes itself from the real data: "97.3 percent hit rate, every write at the 1h TTL, here is what the gap distribution says that choice is worth." Slice 2 is the score and volatile-prefix v2 plus the action column. Slice 3 is the provider notes and a tolkin-cache skill (see gaps). Sizing: slice 1 is one I-phase (reader change, one new module, golden tests, reconciliation); slice 2 is smaller; slice 3 is documentation-weight.

## Gaps neither the build nor the researches saw

1. **Tolkin as the ecosystem's verifier.** The Claude research compiled its vendor-versus-verified table by hand, once, and it is already aging. Tolkin's bench harness is that table as reproducible infrastructure, and it has already independently measured one viral claim (caveman-shrink: 11.72 percent on declared fixtures against its ecosystem's 65 percent headline). Extend deliberately: verify notion-slim's 52 percent, Repomix --compress's ~70 percent, cavemem's unverified 46 percent, and Tool Search's 85 percent (where measurable from manifests) on declared fixtures, and publish a standing "claimed versus measured" section on /bench. No one else occupies the auditor position, and it compounds the trust moat. Size: M.
2. **TTL economics from observed cadence.** Covered fully in the deep dive; listed here because it is the capability neither research realized was possible from local logs, and it is unique to a tool that already ingests them with consent.
3. **Cap-runway forecasting.** The Claude research explains the $50 cap mechanics (line 440) and the observability tooling (line 436), but nothing forecasts. With measured daily burn already in the ledger pipeline (by_day in types.rs), "at your 7-day average you reach $50 on the 23rd" is one division, measured-tier, and is the single number a capped user checks daily. Size: S.
4. **Measure the user's own output share before they buy output compression.** Both researches argue about Caveman's denominator (1-3 percent of bill). Tolkin can end the argument per user: output tokens and output dollars as a share of the session bill, from their own logs (this machine: 9.23M output tokens against 1.72B input-side). "Here is what output compression could possibly save you" is a measured-tier number nobody else shows, and it operationalizes the researches' biggest caveat. Size: S.
5. **A tolkin-cache skill.** The three staged skills teach measurement, slimming, and the optimize loop; none teaches cache hygiene. A fourth skill wrapping `tolkin cache` (read the report, apply prefix-stability fixes with confirmation, re-measure) completes the set and is the distribution channel for the deep-dive work. Size: S, after cache slice 1.
6. **Explicit denominators as a rendered convention.** The researches name denominator games as the field's core dishonesty (CL 481) but propose no convention. Tolkin mostly has one implicitly; making every percentage carry its denominator label everywhere (CLI, web, report, action comment) turns the caveat into a product feature. Size: S.
7. **Privacy-preserving team aggregation.** The researches jump from single-user measurement to gateway-enforced team budgets. There is a missing middle that fits tolkin's posture: `tolkin stats --export` emitting a headline-numbers-only artifact (no paths beyond project labels the user approves, no content) that a lead merges offline into a team view. Local-first governance without a proxy. Size: M, design-sensitive; consent UX is the hard part.
8. **A stated limit on quality regression for config slimming.** The researches caveat accuracy loss from aggressive optimization, and tolkin's lossy track handles compression quality honestly. For config slimming there is no cheap, content-free quality signal (detecting an agent re-asking for a removed tool requires reading content tolkin must not read). The honest move is a documented limitation in the slim skill and docs: slim with the verified mechanisms, watch your own workflows, restore via the recorded snippet. Cheaper than pretending to measure it.

## Testing and launch readiness

**Is the benchmark persuasive to a skeptic?** The structural and lossy tracks, yes: declared fixtures, named tokenizers, zero-variance enforcement, vendored comparators, achieved-versus-target ratios, and the not-runnable rows with reasons are exactly what the methodology promises. Three weaknesses: the configuration track's estimate-versus-measurement gap (P1-3, the one a hostile reader leads with); the fixture corpus is small and self-authored (4/3/3 cases), so add at least one external, widely-recognizable fixture per track; and the lossy track has never published a scored run, so run the BYOK extraction-QA harness once before launch and publish it with scored=true, because "quality scoring exists but has never run" reads as a hedge. P2: the "Runs" column means different things per track (3 transform runs versus 1 compression plus 3 tokenizations; disclosed in prose at RESULTS.md:92 but easy to misread), and the 9-21 versus 14-21 percent Guzik citation needs source verification (see adjudications).

**What a 5-stranger beta reveals that CI cannot.** (1) Catalog hit rate in the wild: the analyzer prices only its 22 matched servers; strangers' configs will measure the unknown-server rate, the number that decides whether tools/list ingestion is urgent. (2) Real Windows behavior beyond `cargo test` (the win32 npm package shipped at 0.9.0 with no recorded end-user smoke on a real Windows box). (3) Whether the two-consent onboarding reads as trustworthy or as friction (the wording is good; only strangers can say if it lands). (4) npx cold-start tolerance: the platform packages are ~10MB; first-run latency on slow networks is a real first-impression risk. (5) Whether tier labels communicate without the README (ask each tester to explain "realized" back; if they cannot, the labels need a glossary tooltip more than the labels need changing).

**Onboarding moments that would lose a non-technical user.** The flow itself is strong (banner, five ticks, two consents, a suggestion card; onboard.rs). Two papercuts: `tolkin stats --json` on a fresh machine prints prose hints instead of JSON (live verified; stats.rs:62-71), which breaks the exact command the skills teach agents to run (P2, easy: emit a valid JSON empty-state when --json is set); and the bare `tolkin` dashboard pre-consent shows setup panels, which is fine, but the suggestion card should also mention `tolkin report --html` since the stakeholder artifact is the thing a non-technical user can actually show someone.

**Does the action's PR comment earn its place in a busy repo?** Close. The sticky upsert, report-only default, step-summary fallback, and least-privilege documentation (action.yml:34-41) are the right manners. It misses the one thing the researches show makes such comments load-bearing instead of wallpaper: the delta. A comment that says "your always-loaded context is 6,976 tokens" every PR gets muted; "this PR adds +4,700 tokens (+33 percent) to static context" gets acted on (GPT 166-190). Add merge-base comparison and a max-delta budget input, then it earns the slot. Also P2: the action pins setup-node to Node 20 (action.yml:49), which is past end-of-life and inconsistent with the repo's own Node-24 posture; bump it.

**Minimal docs surface a public launch needs.** The staged README minus the P1-2 errors; a resolvable methodology link (mirror RESULTS.md into the public repo or link the /bench URL); a short PRIVACY.md stating the posture and the env kills (CI, TOLKIN_NO_LEDGER, TOLKIN_DATA_DIR) since the posture is the differentiator and currently lives only in this monorepo's docs; the tier-vocabulary table (already in the README); and a one-paragraph FAQ on Claude counts being labeled estimates (cl100k proxy, plus-or-minus 10 percent, verify path). Nothing else blocks.

**Overpromise audit, both directions.** Tolkin's public copy echoes no inflated vendor number as its own: the catalog notes attribute third-party figures (Scalekit 65x, notion-slim "about 52%", the 26-55K GitHub range) and the bench page renders only measured rows (grep across distribution/ and the web app found no unattributed 65/90/98.7 percent claims). Three soft spots: the README's "Nothing is promised that has not been measured" is slightly ahead of a product whose Tier 1 numbers are estimates (the tier table two paragraphs later fixes it, but the sentence invites the cheap shot; consider "Nothing is labeled measured that has not been measured"); the /bench page description calls all three tracks "Measured" (P1-3); and the cost calculator's default total (P1-4). In the other direction, the researches contain vendor-inflated numbers tolkin must keep refusing to echo: the 65-75 percent Caveman headline (already handled, methodology.md tells the story correctly), Tool Search's 85 percent (cite with the accuracy caveat), and code-execution's 98.7 percent (cite as vendor-reported if adopted per the matrix row). The honesty rules held; the drift is in staged docs, not in the product's numbers.
